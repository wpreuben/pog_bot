# Phase 2: RTT JSON 기보 정제와 Historical 엔진 교차 재현

## 목적과 합의한 완료 기준

사용자가 제공한 `replays/replay-258629.json`의 Historical 게임을 종료까지 재현하고, 기존 Python 엔진의 의미상 같은 상태가 RTT 기록과 일치하는지 검증한다. 이 게임은 1,447개의 RTT 입력으로 구성되며 8턴에 CP가 항복한다. 입력에는 85개의 `undo`가 있다. 완료 판정은 RTT 자체 재생 성공만으로 하지 않는다. Python 엔진의 합법 행동을 통해 전체 게임을 진행하고 최종 결과까지 대조해야 한다.

원본 JSON을 우선 입력으로 삼는다. 최상위 `LOG1.txt`는 사용자 요청에 따라 삭제했다. Phase 1의 `tests/fixtures/LOG1.txt`와 관련 회귀 테스트는 규칙 회귀 사례를 독립적인 구성 상태 테스트로 보존한 뒤 제거한다. `LOG1`은 258629번과 다른 게임이므로 두 기록을 하나의 기보로 합치지 않는다.

공식 2022 Deluxe 영문 룰북이 규칙 해석의 기준이다. RTT는 행동·관측 자료이며, 결과가 다르면 원인을 기록하고 룰북에 맞는 엔진 동작을 유지한다. Python 엔진의 공개 계약인 `create_game`, `generate_legal_actions`, `apply_action`, `replay`를 사용한다.

## 확인된 입력과 접근 선택

JSON 최상위에는 `setup`, `players`, `state`, `replay`가 있다. 첫 기록은 시드와 시나리오를 담은 `.setup`이고, 이후 기록은 `[역할, 화면 행동, 선택적 인수]` 배열이다. `piece`, `space`, `done`, `undo` 등 화면 단위 입력은 Python 엔진의 행동과 일대일로 대응하지 않는다. 마지막 기록은 `.resign`이다. 제공된 RTT `rules.js`로 모든 1,447개 입력을 적용하면 내보낸 상태의 턴(8), VP(7), 게임 종료, 승리 문구, RNG 시드가 일치한다. 플랫폼이 채우는 `active`·`result` 표현과 항복 직전 로그의 공백 줄은 별도 정규화가 필요하다.

세 접근을 검토했다. 텍스트 로그만 파싱하면 시드·주사위·개별 유닛 ID를 알 수 없어 완전 재현이 불가능하다. RTT 화면 입력을 즉시 Python 행동으로 치환하면 되돌리기와 다단계 선택의 중간 상태가 섞인다. **구조화 JSON을 RTT에서 먼저 재생하고, 확정된 의미 행동과 관측 상태를 Python 엔진에 대응시키는 방식**을 선택한다. `LOG1` 텍스트 파서는 이번 완료 범위에 넣지 않는다.

## 구성 요소와 데이터 흐름

```text
원본 JSON → 형식 검사 → RTT 재생/관측 추출 → 확정 행동 정제
                                       ↓
RTT ID 대응표 → Python 합법 행동 매칭 → apply_action → 의미 상태 대조
                                               ↓
                                    첫 차이 보고서 + 재현 기록
```

1. **입력 파서**는 JSON 형식, `Historical` 시나리오, `.setup` 인수, 역할, 행동 인덱스와 인수 형식을 검사한다. 외부 입력을 코드로 실행하지 않는다. `players`의 이름은 기보 의미에 필요하지 않으며 저장할 테스트 자료에서는 제외한다.
2. **RTT 관측기**는 기존 JavaScript `rules.js`의 `setup`·`action`·`resign`으로 원본 입력을 순서대로 적용한다. 원본 소스를 수정하거나 Python 엔진에 포함하지 않는다. 각 입력 전후의 필요한 상태와 로그 증분을 제한된 JSON 형식으로 내보낸다. 내보낸 최종 `state`와 비교할 때 플랫폼 직렬화 차이는 명시적으로 정규화한다.
3. **정제기**는 카드 사용, 이동·공격 활성화, 유닛 선택, 전투 하위 선택, SR, RP, 주사위, 턴 경계와 항복을 의미 행동으로 묶는다. `undo`가 취소한 미확정 선택은 Python 엔진에 전달하지 않는다. 각 정제 항목에는 원본 입력 범위, 역할, RTT 관측 전후 상태, 필요한 난수 관측을 보존한다. 추측으로 누락된 선택을 채우지 않는다.
4. **ID 변환기**는 기존 `source_ids.json`의 RTT 숫자 카드·유닛·공간 ID를 Python ID로 변환한다. 중복 유닛은 개별 ID를 유지한다. ID가 없거나 일대다 매핑이면 조용히 임의 선택하지 않고 진단을 반환한다.
5. **Python 재생기**는 `generate_legal_actions`에서 정제 항목과 맞는 행동을 찾고 `apply_action`을 호출한다. 후보가 없거나 둘 이상이면 중단하고 첫 불일치를 보고한다. 성공한 전이는 기존 `Transition.record` 형식으로 보존해 `replay`로 결정성을 재검증한다.
6. **상태 투영·대조기**는 양쪽 구현의 서로 다른 내부 구조를 같은 의미 필드로 투영한다. RTT의 UI 선택 상태, `undo` 스택, 로그 공백과 Python의 내부 결정 객체는 동등성 비교에서 제외한다. 턴·라운드, VP, 손패·덱·버림·제거 카드, 유닛의 위치·감소·제거, 공간 통제·참호·요새, 참전·전쟁 상태, RP와 주요 이벤트, 게임 종료 결과를 비교한다. 숨김 정보는 테스트 전용 전체 상태에서만 비교한다.

## 초기 상태, 난수, 되돌리기

두 구현의 섞기 알고리즘이 다르므로 같은 `.setup` 시드로 만든 손패·덱이 같다고 가정하지 않는다. 먼저 RTT `.setup` 직후 상태와 Python `create_game`의 지도·유닛·규칙상 초기 상태를 대조한다. 재현용 Python 상태에는 RTT에서 관측한 손패·덱 순서를 ID 변환 후 주입한다. 이 조정은 재생 어댑터 경계에 한정하며, 일반 `create_game`의 동작을 바꾸지 않는다.

주사위 결과는 RTT 재생에서 관측한 굴림 순서를 보존해 Python의 `CHANCE` 행동에 명시적으로 전달한다. 턴이 지나며 발생하는 섞기·드로우도 RTT 관측 상태와 대조한다. 필요한 경우 재생 어댑터가 카드 순서를 주입하는 명시적 인터페이스를 사용하고, 엔진이 임의로 다른 결과를 만들도록 방치하지 않는다. 관측 로그만으로 굴림을 구분할 수 없으면 RTT의 RNG 호출 또는 전후 상태를 계측해 정확한 값을 확보한다. 계측이 실패하면 재생 불가능한 위치를 보고한다.

RTT의 85개 `undo`는 관측기에서 모두 처리한다. 정제기는 되돌려진 화면 선택을 버리고 최종적으로 확정된 선택만 Python 엔진에 보낸다. 어느 확정 경계에 묶였는지는 원본 인덱스로 추적한다. `.resign`은 보드 규칙과 별개인 게임 종료 행동으로 다룬다. Python 엔진에 합법적인 `RESIGN` 행동을 추가해 CP 항복과 AP 승리 결과를 기록하며, RTT 종료 상태와 비교한다.

## 오류 처리와 차이 보고

오류는 입력 형식 오류, 매핑 누락·모호성, 정제 실패, Python 불법 행동, 상태 불일치, 룰북과 RTT의 규칙 차이로 구분한다. 실행은 첫 재현 불일치에서 멈춰 원인을 찾기 쉽게 한다. 보고서에는 게임 ID, RTT 입력 번호·행동, 해당 정제 항목, Python 단계·결정 창, 후보 합법 행동, 첫 차이 상태 경로, 기대값과 실제값을 담는다. 이름 등 `players` 개인정보와 상대 손패를 사용자용 요약에 노출하지 않는다. 룰북 차이는 해당 조항과 재현 가능한 최소 사례를 별도 문서에 기록한다.

## 검증과 완료 판정

- 파서가 제공된 JSON을 읽고 손상된 레코드, 지원하지 않는 시나리오, 알 수 없는 역할·ID에 대해 정확한 인덱스의 오류를 낸다.
- RTT 관측기가 1,447개 입력과 `undo` 85개를 모두 처리하고, 내보낸 최종 상태를 정규화 후 일치시킨다.
- 정제된 확정 행동을 Python의 합법 행동으로 끝까지 적용한다. 각 의미 경계에서 투영 상태를 비교하고, 최종 턴 8·VP 7·CP 항복·AP 승리를 확인한다.
- 저장한 `Transition.record` 배열을 독립적으로 다시 `replay`해 동일한 Python 최종 상태를 얻는다.
- 기존 Phase 1 전체 테스트와 `uv lock --check`를 통과한다. `LOG1`에만 의존하던 규칙 회귀 사례는 원문 파일 없이 독립 실행되도록 고친 다음 원문 복사본과 관련 문서를 제거한다.
- 원본 JSON은 사용자 작업 폴더의 입력으로 다룬다. 저장소에는 이름을 제거한 최소 재현 자료와 생성 방법만 넣어, 게임 재현에 필요 없는 `players` 필드를 커밋하지 않는다.

완료 전에 전체 게임을 맞출 수 없는 규칙 차이가 발견되면 이를 성공으로 표시하지 않는다. 공식 룰북 근거에 따라 Python 엔진을 수정할지 RTT 차이로 기록할지 결정하고, 해당 지점의 회귀 테스트를 추가한다.
